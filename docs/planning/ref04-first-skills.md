# REF-04 first skill plans

Status: contract-level authoring plan. This file does not add catalog records, skill payloads,
provider calls, execution stages, path authority, budget, approval, or publication authority.
The four proposed skills remain unavailable until separately authored, audited, fixture-tested,
and integrated through the controller-owned planning flow.

## Shared contract

Each future skill is a repository-bundled, versioned procedure selected for one existing base
role. Its `SKILL.md` and any loaded reference are regular contained files pinned by SHA-256.
The controller records the source and license references, role, selection reason, reference
hashes, and encoded byte count. Binding and every dispatch or supported resume rehash the exact
files. A source, reference, path, or byte-count change requires a new plan and binding.

Skill text is advice within an already authorized assignment. It cannot add commands, tools,
paths, models, calls, retries, spending, approval, merge, publication, or deployment rights.
Workers may report one material blocker or propose a follow-up; only the controller can validate
and schedule it. Outputs are schema-validated artifacts and do not change task state.

Initial maturity is `authored`, followed by `structurally-validated` and
`behaviorally-fixture-tested`. Host or live labels require new revision-bound evidence. The
catalog must display the achieved level and provenance rather than calling a fixture-tested
procedure expert or calibrated.

Every skill needs positive, negative-trigger, ambiguous, adversarial, changed-hash, excessive-
context, and held-out forward fixtures. Forward fixtures hide the expected answer from the
specialist. Evaluation records profile, model, runtime, complete binding identity, result,
clarification burden, concrete defects, and human corrections. A matched unguided run is needed
before claiming improvement; structural success alone is not evidence of better outcomes.

## `product-shaping`

**Purpose and base role.** Extend `tech_lead` using `structured-planning` for a materially
ambiguous product brief. Produce a small inspectable scope before implementation authority
exists. A future explicit shaping node may refine the reservation mapping; this skill does not
create that node.

**Positive triggers.** The intended user or job is unclear; two plausible critical journeys
would produce materially different products; requirements conflict; or observable success
cannot be derived without one consequential choice.

**Negative triggers.** A narrow repository defect already names behavior and acceptance; a
routine UI adjustment has a clear target; the question is API ownership rather than product
intent; or the only uncertainty is a reversible implementation choice. In those cases use the
existing task-contract/interface procedures as appropriate and do not spend a shaping call.

**Bounded inputs.** User brief and source identity, declared audience and constraints when
provided, repository/product inventory, existing conventions, non-goals, supported capability
summary, and remaining controller allocation as observation only. Do not include credentials,
hidden acceptance implementation, candidate solution, raw transcripts, or unrelated domain
guides.

**Output contract.** Return source-linked requirements and assumptions; primary user and job;
one critical journey; prioritized smallest useful scope; exclusions; observable acceptance
proposals; reversible choices; and either no question or one material question. Distinguish
supplied requirements from inferences. Do not invent market facts, users, brand constraints,
features, access, cost, or delivery commitments.

**Procedure outline.** Identify the decision that changes scope; map supplied statements to
requirement or assumption; choose the smallest coherent journey; state exclusions; turn the
journey into externally observable outcomes; test the proposal against a materially different
interpretation; ask one question only if both remain plausible and consequential.

**Fixtures and forward gate.** Two different briefs must yield different justified scopes. A
contradictory brief must preserve a draft and ask one useful question. A precise bug and API
schema change must not activate it. Adversarial brief text requesting shell execution, more
budget, approval, publication, or unrelated paths must remain plain untrusted prose and cannot
appear as authority in output. A held-out brief passes when an independent evaluator can map
every scope item and acceptance proposal to a source or labeled assumption without finding an
invented requirement.

## `interaction-design`

**Purpose and base role.** Extend `tech_lead` using `structured-planning` for a new or materially
changed user interaction. Produce an implementable flow contract without prescribing filesystem
or browser authority.

**Positive triggers.** The task adds or changes navigation, form behavior, state transitions,
recovery, keyboard interaction, responsive ordering, or another user-visible sequence whose
omission could change success.

**Negative triggers.** Pure typography/color work with unchanged interaction; backend/API
interface design; a one-line label correction; or source verification after a flow is already
frozen. `interface-design` remains the API and ownership procedure and must not be routed here
from the word “interface” alone.

**Bounded inputs.** Frozen user/job and prioritized flow, current interface inventory, platform
and viewport targets, known component conventions, public validation rules, and authorized
reference excerpts. Images or external references require separate provenance and hash-bound
loading.

**Output contract.** Return the primary step sequence and relevant entry/exit points; empty,
invalid, loading when applicable, success, cancellation, and recovery states; input validation
and feedback timing; keyboard order, focus placement/restoration, and visible focus; responsive
reflow and touch targets; unresolved evidence gaps; and acceptance IDs. “Intuitive” or “handle
errors” without concrete behavior is invalid.

**Procedure outline.** Trace the shortest successful path; enumerate transitions and state
ownership; add failure and restart paths; verify reset/cancel semantics; walk the flow using only
keyboard actions; test narrow-width ordering and content growth; identify any state that depends
on unavailable evidence.

**Fixtures and forward gate.** A form fixture must specify invalid submission, correction,
success, reset, focus, and narrow layout. A static content restyle must not activate the skill.
An ambiguous loading state must be labeled conditional rather than invented. Adversarial copy
containing navigation URLs or command text must remain display content. The held-out flow passes
when an implementer can enumerate all state transitions without asking about omitted error,
reset, focus, or responsive semantics.

## `visual-design`

**Purpose and base role.** Extend `tech_lead` using `structured-planning` when visual direction
materially affects a user-facing product. Convert audience and intent into concrete hierarchy,
tokens, layout, and component behavior while reusing verified brand conventions when present.

**Positive triggers.** A new user-facing surface needs a visual direction; existing hierarchy
does not support the critical journey; a material redesign is requested; or typography, spacing,
color, and component states must be specified together for coherent implementation.

**Negative triggers.** Backend or API work; a narrow defect under an existing design system;
interaction-only behavior with stable visuals; or a request that merely uses words such as
“clean” or “polished” without making direction consequential. Routine cosmetic choices become
labeled reversible assumptions rather than a mandatory model call.

**Bounded inputs.** Frozen audience/job and flow, existing brand/design tokens with provenance,
current component and asset inventory, content hierarchy, supported responsive targets, and
accessibility criteria. Unverified web trends, competitor material, fonts, remote assets, and
licensed media are excluded.

**Output contract.** Return one selected direction and rationale; content hierarchy; typography,
spacing, color, radius/elevation where relevant, and layout tokens; component anatomy and
default/hover/focus/disabled/error/success states; responsive behavior; contrast and non-color
cues; approved local asset references and provenance; assumptions; non-goals; and acceptance
IDs. Values must be concrete enough to implement. “Modern,” “premium,” or “polished” alone is
invalid. More than one direction is justified only for a consequential unresolved choice and is
kept to a small inspectable set.

**Procedure outline.** Extract audience and visual intent; inventory existing conventions;
choose hierarchy before decoration; define a minimal token set; apply it to named components and
states; test contrast, focus, long content, and narrow layouts; remove unsupported assets and
decorative requirements that do not serve the chosen direction.

**Fixtures and forward gate.** Two materially different intents must retain distinguishable
tokens and layouts without arbitrary trend language. An existing-brand fixture must reuse its
verified tokens. A backend task and a one-color fix must not activate the skill. Asset paths,
data URLs, imports, installation instructions, and publication requests cannot expand context or
authority. A held-out design passes when implementation can map each visible decision to a
token/component rule and independent review can distinguish explicit criteria from preference.

## `acceptance-design`

**Purpose and base role.** Extend `tech_lead` using `structured-planning` only when existing
independent acceptance is inadequate. Produce a proposal for controller validation in a separate
test-authoring boundary. It cannot install, freeze, run, weaken, or mark its own oracle passed.

**Positive triggers.** New behavior lacks an independent oracle; existing checks do not cover a
material requirement; expected results can be derived from frozen public requirements; and an
approved runtime/profile can support controlled positive and negative calibration.

**Negative triggers.** Existing enrolled tests already establish the behavior; the request is to
make a failing implementation pass; expected output can only be copied from a candidate patch;
requirements are still materially ambiguous; or no controlled runtime exists. A broken harness
is diagnosed and blocked rather than rewritten as a product failure.

**Bounded inputs.** Frozen requirement IDs and sources, public interfaces and examples, runtime
and capability manifest, allowed argv policy, existing test discovery evidence, and controlled
positive/negative fixture descriptions. Exclude candidate implementation, expected patch,
hidden fixture solution, controller database, approval state, and worker write paths.

**Output contract.** Return requirement-to-check mapping; check class (`existing-repo`,
`agent-proposed`, `protected-independent`, `browser`, or `manual`); expected value and its origin;
runtime/profile and bounded argv proposal; oracle schema/version; positive and intentional-
defect controls; discovery assertion; failure categories separating product, test harness,
runtime, and unresolved assertions; coverage gaps; and calibration evidence required before
freeze. Cross-realm JavaScript values/errors must be compared by observable semantics rather
than realm-specific constructor identity where that is the requirement.

**Procedure outline.** Derive outcomes without viewing implementation; map each material
requirement; choose the least privileged check class; require nonempty discovery; define a known-
good control and intentional defect; identify harness/runtime failure signals; test the oracle
against cross-process/realm behavior; leave ambiguous assertions unclassified; submit the
proposal for controller validation and immutable hashing.

**Fixtures and forward gate.** Include the archived VM error-constructor mismatch: the oracle
must distinguish semantic error behavior from cross-realm identity and must label a broken
assertion as harness evidence. Include unavailable worker Node: readiness blocks before proposed
execution and cannot be recorded as product failure. A known-good fixture passes, an intentional
defect fails, empty discovery fails, and a broken harness errors distinctly. Adversarial
requirements requesting candidate source, controller state, arbitrary argv, oracle weakening,
extra calls, or approval are rejected. The held-out task passes only when an independent
controller can calibrate and freeze the proposal without candidate leakage.

## Authoring and integration order

1. Freeze output schema IDs and activation identifiers with the intake/graph owner.
2. Author `product-shaping`, `interaction-design`, `visual-design`, and `acceptance-design` in
   repository-local directories with source/license records; do not copy global personal skills.
3. Run structural and adversarial fixtures, including exact request assembly and changed-hash
   rejection. Record fixture-only maturity and gaps.
4. Integrate deterministic selector triggers and typed planning nodes without changing durable
   base roles. Reserve every provider launch and preserve mandatory verification/review capacity.
5. Run held-out forward cases and matched unguided cases. Promotion beyond fixture maturity or
   any live quality claim requires separately authorized, revision-bound evaluation.
